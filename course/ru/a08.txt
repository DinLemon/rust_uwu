# MODULE a08 | Потоки глубже | Send и Sync, scope, RwLock, атомики и rayon

## LESSON a08-1 | Send и Sync | 7
:: goals
- Понять, кто решает, что можно отдать в поток
- Знать, почему `Rc` нельзя, а `Arc` можно

:: text Два трейта-метки
У Rust есть два трейта без методов. Компилятор ставит их типам **сам**:
- `Send` — значение можно **переслать** в другой поток (передать владение).
- `Sync` — на значение можно **смотреть** из нескольких потоков сразу (делиться `&T`).

Почти всё вокруг — `Send` и `Sync`: числа, `String`, `Vec`. Исключения — типы, которые небезопасны при одновременной работе.

> **Аналогия:** `Send` — вещь можно отправить посылкой. `Sync` — вещь можно повесить на общую доску, и все будут на неё смотреть одновременно.

:: text Почему Rc — не Send
`Rc` считает владельцев **обычным** числом. Если два потока одновременно сделают `clone`, счётчик может сбиться: оба прочитают 1, оба запишут 2, хотя должно быть 3. Потом память освободится раньше времени.

Поэтому `Rc` не `Send`, и компилятор не даст отправить его в поток. Вместо него — `Arc` (atomic Rc): он считает владельцев **атомарно**, без сбоев. Он чуть медленнее, зато безопасен.

:: code
```rust
use std::sync::Arc;
use std::thread;

fn main() {
    let shared = Arc::new(vec![1, 2, 3]);
    let mut handles = vec![];
    for i in 0..3 {
        let data = Arc::clone(&shared);
        handles.push(thread::spawn(move || data[i] * 10));
    }
    let results: Vec<i32> = handles.into_iter().map(|h| h.join().unwrap()).collect();
    println!("{results:?}");
}
```
```out
[10, 20, 30]
```
Замени `Arc` на `std::rc::Rc` и запусти. Ошибка скажет: `Rc<Vec<i32>>` cannot be sent between threads safely.

:: quiz
Почему `Rc` нельзя отправить в другой поток?
[ ] Потому что он хранит данные в куче => `Arc` тоже хранит в куче, и его можно.
[x] Его счётчик владельцев может сбиться при одновременных изменениях => Верно. `Arc` считает атомарно.
[ ] Потому что он медленный => Наоборот, `Rc` быстрее `Arc`.

:: text Ещё пары «не для потоков» и «для потоков»
- `Rc` → `Arc`
- `RefCell` → `Mutex` или `RwLock`
- `Cell` → атомики (`AtomicUsize`, `AtomicBool`…)

Правило: если тип «однопоточный», у него есть многопоточный брат.

:: deep Как компилятор ставит Send и Sync
`Send` и `Sync` — **автоматические** трейты. Структура получает их сама, если **все её поля** их имеют. Достаточно одного поля `Rc` внутри — и вся структура уже не `Send`.

Есть точное правило: `T` — `Sync`, если `&T` — `Send`. То есть «делиться ссылкой безопасно» = «ссылку можно переслать в другой поток».

Вручную реализовать эти трейты можно только через `unsafe impl Send for T {}`. Это обещание компилятору, что ты сам всё проверил. Нужно редко — в основном авторам низкоуровневых библиотек.

:: recap
- `Send` — можно передать в поток, `Sync` — можно делиться ссылкой между потоками.
- Компилятор ставит их сам по полям.
- `Rc`/`RefCell` — однопоточные; `Arc`/`Mutex` — их многопоточные братья.

## LESSON a08-2 | thread::scope: потоки, которые одалживают | 7
:: goals
- Запускать потоки, которые читают локальные данные без `Arc` и `move`
- Понять, почему это безопасно

:: text Проблема spawn
`thread::spawn` требует `'static`: поток может пережить функцию. Поэтому приходится всё перемещать или оборачивать в `Arc`. Даже если поток живёт пару миллисекунд.

`thread::scope` решает это: все потоки внутри «области» **обязательно** заканчиваются до выхода из неё. Значит, они могут спокойно одалживать локальные переменные.

> **Аналогия:** детский праздник в квартире. Все гости уходят до того, как ты закроешь дверь. Поэтому им можно дать твои игрушки — они точно вернутся.

:: code
```rust
use std::thread;

fn main() {
    let numbers = vec![1, 2, 3, 4, 5, 6];
    let (left, right) = numbers.split_at(3);

    let (a, b) = thread::scope(|s| {
        let h1 = s.spawn(|| left.iter().sum::<i32>());
        let h2 = s.spawn(|| right.iter().sum::<i32>());
        (h1.join().unwrap(), h2.join().unwrap())
    });

    println!("{a} + {b} = {}", a + b);
    println!("вектор всё ещё наш: {}", numbers.len());
}
```
```out
6 + 15 = 21
вектор всё ещё наш: 6
```
Ни `Arc`, ни `move`, ни `clone`. Потоки просто смотрят на половинки вектора.

:: text Можно и менять
Внутри `scope` поток может взять даже `&mut` — если только он один:

```rust
let mut counts = [0; 2];
thread::scope(|s| {
    let (a, b) = counts.split_at_mut(1);
    s.spawn(|| a[0] += 1);
    s.spawn(|| b[0] += 2);
});
// counts == [1, 2]
```
`split_at_mut` делит массив на две **непересекающиеся** части. Каждый поток меняет свою.

:: quiz
Почему внутри `thread::scope` потоки могут брать ссылки на локальные переменные?
[x] Все потоки области обязательно завершатся до выхода из неё => Верно. Ссылки не переживут данные.
[ ] Потому что там отключены проверки => Проверки работают как обычно.
[ ] Потому что данные копируются в каждый поток => Ничего не копируется.

:: task
Посчитай в двух потоках внутри `thread::scope`: в первом — сколько чётных чисел, во втором — сколько нечётных. Напечатай `чётных 3, нечётных 4`.
```rust
use std::thread;

fn main() {
    let v = vec![1, 2, 3, 4, 5, 6, 7];
    // твой код
}
```
```solution
use std::thread;

fn main() {
    let v = vec![1, 2, 3, 4, 5, 6, 7];
    let (even, odd) = thread::scope(|s| {
        let e = s.spawn(|| v.iter().filter(|x| *x % 2 == 0).count());
        let o = s.spawn(|| v.iter().filter(|x| *x % 2 == 1).count());
        (e.join().unwrap(), o.join().unwrap())
    });
    println!("чётных {even}, нечётных {odd}");
}
```
```expect
чётных 3, нечётных 4
```
hint: `thread::scope(|s| { ... })` — внутри `s.spawn(|| ...)`. Результат области — то, что вернул блок.
hint: Верни пару: `(e.join().unwrap(), o.join().unwrap())`.

:: recap
- `thread::scope` — потоки заканчиваются до выхода из области.
- Поэтому им можно давать `&` и даже `&mut` на локальные данные.
- Не нужен ни `Arc`, ни `move`.

## LESSON a08-3 | RwLock и атомики | 8
:: goals
- Выбирать между `Mutex` и `RwLock`
- Считать что-то в потоках без замка — атомиками

:: text RwLock: много читателей или один писатель
`Mutex` пускает к данным **одного** — неважно, читает он или пишет. Если читают часто, а пишут редко, это лишняя очередь.

`RwLock` (read-write lock) пускает:
- **сколько угодно** читателей одновременно — `read()`;
- или **одного** писателя — `write()`.

> **Аналогия:** музей. Смотреть картины могут сразу многие. Но когда реставратор работает с картиной, зал закрыт для всех.

:: code
```rust
use std::sync::{Arc, RwLock};
use std::thread;

fn main() {
    let config = Arc::new(RwLock::new(String::from("тёмная тема")));

    let readers: Vec<_> = (0..3).map(|_| {
        let c = Arc::clone(&config);
        thread::spawn(move || c.read().unwrap().len()) // читают одновременно
    }).collect();
    for r in readers {
        r.join().unwrap();
    }

    {
        let mut w = config.write().unwrap();
        *w = String::from("светлая тема");
    }
    println!("{}", config.read().unwrap());
}
```
```out
светлая тема
```

:: text Атомики: без замка вообще
Для простых вещей — счётчик, флаг — замок не нужен. Есть **атомарные** типы: `AtomicUsize`, `AtomicBool`, `AtomicI64`… Их операции процессор выполняет «за один неделимый шаг».

```rust
use std::sync::atomic::{AtomicUsize, Ordering};

let hits = AtomicUsize::new(0);
hits.fetch_add(1, Ordering::Relaxed); // +1, безопасно из любых потоков
let n = hits.load(Ordering::Relaxed);
```
`Ordering::Relaxed` — для простых счётчиков этого хватает. Что это значит — в углублении.

:: code
```rust
use std::sync::atomic::{AtomicUsize, Ordering};
use std::thread;

fn main() {
    let hits = AtomicUsize::new(0);
    thread::scope(|s| {
        for _ in 0..4 {
            s.spawn(|| {
                for _ in 0..1000 {
                    hits.fetch_add(1, Ordering::Relaxed);
                }
            });
        }
    });
    println!("{}", hits.load(Ordering::Relaxed));
}
```
```out
4000
```
Четыре потока по тысяче раз — ровно 4000, без замка. Заметь: атомик меняют через `&`, `mut` не нужен.

:: quiz
Данные часто читают из многих потоков и редко меняют. Что лучше?
[ ] `Mutex` => Подойдёт, но читатели будут ждать друг друга зря.
[x] `RwLock` => Верно. Читатели не мешают друг другу.
[ ] `RefCell` => Он не для потоков.

:: quiz
Нужен общий счётчик запросов для всех потоков. Что проще всего?
[x] `AtomicUsize` => Верно. Ни замка, ни `mut`.
[ ] `Arc<Rc<usize>>` => `Rc` нельзя в потоки, и менять через него нельзя.
[ ] Обычный `usize` в `static mut` => Небезопасно и требует `unsafe`.

:: deep Что такое Ordering
Процессор и компилятор **переставляют** операции ради скорости, если в одном потоке это незаметно. Но другой поток может увидеть изменения не в том порядке, в каком ты их написал.

`Ordering` говорит, какой порядок нужно сохранить:
- `Relaxed` — только сама операция неделима, порядок с остальными не гарантирован. Для счётчиков хватает.
- `Release` (при записи) + `Acquire` (при чтении) — «всё, что я сделал до записи, будет видно тому, кто прочитал». Так строят флаги «данные готовы».
- `SeqCst` — самый строгий: все потоки видят один общий порядок. Медленнее, но проще думать.

Не уверен — бери `SeqCst`. Хочешь глубже — книга Mara Bos «Rust Atomics and Locks» (бесплатно онлайн).

:: recap
- `RwLock`: много `read()` одновременно или один `write()`.
- Атомики (`AtomicUsize`…) — счётчики и флаги без замка.
- Для простого счётчика — `fetch_add(1, Ordering::Relaxed)`.

## LESSON a08-4 | rayon: параллельно одной буквой | 6
:: goals
- Распараллелить вычисления, поменяв `iter` на `par_iter`
- Понимать, когда это ускоряет, а когда нет

:: text Параллельный итератор
Крейт **rayon** берёт обычную цепочку итераторов и раскидывает работу по всем ядрам процессора. Чаще всего изменение — одно слово:

```rust
use rayon::prelude::*;

let sum: u64 = data.iter().map(heavy).sum();     // одно ядро
let sum: u64 = data.par_iter().map(heavy).sum(); // все ядра
```
rayon сам делит данные на куски, сам создаёт потоки и сам собирает результат.

> **Аналогия:** чистить мешок картошки одному или позвать всю семью. Мешок делят на кучки, и каждый чистит свою.

:: code
```rust
use rayon::prelude::*;

fn is_prime(n: u64) -> bool {
    n >= 2 && (2..).take_while(|d| d * d <= n).all(|d| n % d != 0)
}

fn main() {
    let count = (1..200_000u64).into_par_iter().filter(|&n| is_prime(n)).count();
    println!("простых: {count}");

    let words = vec!["ржавчина", "краб", "ферр"];
    let lens: Vec<usize> = words.par_iter().map(|w| w.chars().count()).collect();
    println!("{lens:?}");
}
```
crates: yes
```out
простых: 17984
[8, 4, 4]
```
`collect` в `par_iter` сохраняет **исходный порядок**, хотя считали параллельно.

:: text Когда это не поможет
- Работы мало (сложить 100 чисел). Раздать задания дольше, чем сделать.
- Каждый шаг ждёт сеть или диск. Тут нужен async, а не больше ядер.
- Шаги зависят друг от друга (каждый следующий использует предыдущий).

Правило: сначала **измерь** (модуль про скорость), потом параллель.

:: quiz
Ты сложил 10 чисел через `par_iter`, и стало медленнее. Почему?
[x] Раздача работы по потокам дороже самой работы => Верно. Параллель окупается на больших объёмах.
[ ] rayon сломан => rayon в порядке, просто задача слишком маленькая.
[ ] Числа сложились неправильно => Результат правильный, просто медленнее.

:: recap
- rayon: `iter()` → `par_iter()`, `into_iter()` → `into_par_iter()`.
- Порядок в `collect` сохраняется.
- Помогает на тяжёлых вычислениях, не помогает на мелочах и ожидании сети.

## LESSON a08-p | Практика: потоки | 14 | practice
:: goals
- Решить задачи с `scope`, атомиками и `RwLock`

:: task
Раздели вектор на 4 куска через `chunks` и посчитай сумму каждого в своём потоке внутри `thread::scope`. Сложи результаты и напечатай.
```rust
use std::thread;

fn main() {
    let data: Vec<u64> = (1..=100).collect();
    // твой код
}
```
```solution
use std::thread;

fn main() {
    let data: Vec<u64> = (1..=100).collect();
    let total: u64 = thread::scope(|s| {
        let handles: Vec<_> = data.chunks(25).map(|c| s.spawn(move || c.iter().sum::<u64>())).collect();
        handles.into_iter().map(|h| h.join().unwrap()).sum()
    });
    println!("{total}");
}
```
```expect
5050
```
hint: `data.chunks(25)` даёт 4 куска. Для каждого — `s.spawn(move || c.iter().sum::<u64>())`.
hint: `move` тут забирает только ссылку на кусок `c`, сами данные остаются в `data`.

:: task
Флаг остановки: `AtomicBool`. Рабочий поток считает до 1000, но проверяет флаг и останавливается, если он поднят. Флаг поднимаем **до** запуска потока, поэтому поток не сделает ни шага.
```rust
use std::sync::atomic::{AtomicBool, Ordering};
use std::thread;

fn main() {
    let stop = AtomicBool::new(false);
    // подними флаг
    let done = thread::scope(|s| {
        s.spawn(|| {
            let mut n = 0;
            while n < 1000 {
                // проверь флаг
                n += 1;
            }
            n
        }).join().unwrap()
    });
    println!("сделано шагов: {done}");
}
```
```solution
use std::sync::atomic::{AtomicBool, Ordering};
use std::thread;

fn main() {
    let stop = AtomicBool::new(false);
    stop.store(true, Ordering::SeqCst);
    let done = thread::scope(|s| {
        s.spawn(|| {
            let mut n = 0;
            while n < 1000 {
                if stop.load(Ordering::SeqCst) {
                    break;
                }
                n += 1;
            }
            n
        }).join().unwrap()
    });
    println!("сделано шагов: {done}");
}
```
```expect
сделано шагов: 0
```
hint: Поднять: `stop.store(true, Ordering::SeqCst)`. Проверить: `if stop.load(Ordering::SeqCst) { break; }`.

:: task
Общий словарь `Arc<RwLock<Vec<String>>>`. Три потока **добавляют** по одному имени через `write()`. Потом главный поток через `read()` сортирует копию и печатает.
```rust
use std::sync::{Arc, RwLock};
use std::thread;

fn main() {
    let names = Arc::new(RwLock::new(Vec::new()));
    let mut handles = vec![];
    for n in ["Вика", "Аня", "Боря"] {
        // твой код
    }
    for h in handles {
        h.join().unwrap();
    }
    let mut sorted = names.read().unwrap().clone();
    sorted.sort();
    println!("{sorted:?}");
}
```
```solution
use std::sync::{Arc, RwLock};
use std::thread;

fn main() {
    let names = Arc::new(RwLock::new(Vec::new()));
    let mut handles = vec![];
    for n in ["Вика", "Аня", "Боря"] {
        let names = Arc::clone(&names);
        handles.push(thread::spawn(move || {
            names.write().unwrap().push(n.to_string());
        }));
    }
    for h in handles {
        h.join().unwrap();
    }
    let mut sorted = names.read().unwrap().clone();
    sorted.sort();
    println!("{sorted:?}");
}
```
```expect
["Аня", "Боря", "Вика"]
```
hint: В каждом шаге цикла: склонируй `Arc`, запусти `thread::spawn(move || ...)` и положи поток в `handles`.
hint: Внутри потока: `names.write().unwrap().push(n.to_string());`.

:: recap
- `scope` + `chunks` — простое деление работы.
- `AtomicBool` — флаг остановки без замка.
- `RwLock::write()` — менять, `read()` — читать.
