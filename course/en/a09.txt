# MODULE a09 | Async from the inside | Future, a tiny runtime of your own, tokio, join, spawn, select

## LESSON a09-1 | What a Future is | 8
:: goals
- See that an `async fn` returns a "promise", not a result
- See that a Future does nothing until it's polled

:: text The main idea again
In Level 1 we said: async means "wait without sitting idle". While one task waits for the network, another one works.

Now let's look inside. Calling an `async fn` **doesn't run it**. It returns a **Future** — an object meaning "the result comes later".

> **Analogy:** a coat-check ticket. You get it right away, and the coat when your turn comes. The ticket won't fetch the coat by itself: you need the attendant.

:: text How a Future works
The `Future` trait has one main method — `poll`:

```rust
trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context) -> Poll<Self::Output>;
}
```
`poll` returns:
- `Poll::Ready(value)` — done;
- `Poll::Pending` — not yet, call me later.

Someone has to call `poll`. That someone is called a **runtime** (or executor). The most popular one is `tokio`.

:: code
A tiny runtime of our own — 10 lines. It just polls the Future until it says "ready":
```rust
use std::future::Future;
use std::pin::pin;
use std::task::{Context, Poll, Waker};

fn block_on<F: Future>(fut: F) -> F::Output {
    let mut fut = pin!(fut);
    let mut cx = Context::from_waker(Waker::noop());
    loop {
        if let Poll::Ready(v) = fut.as_mut().poll(&mut cx) {
            return v;
        }
    }
}

async fn add(a: i32, b: i32) -> i32 {
    println!("computing");
    a + b
}

fn main() {
    let f = add(2, 3);
    println!("future created");
    let r = block_on(f);
    println!("result: {r}");
}
```
```out
future created
computing
result: 5
```
Look at the order: `computing` appeared **after** `future created`. Calling `add(2, 3)` computed nothing — it only created the Future.

:: quiz
What happens if you call an `async fn` and don't `.await` it (or hand it to a runtime)?
[ ] The function runs in the background => Without polling, a Future does nothing.
[x] Nothing: the function body never starts => Right. Futures are lazy.
[ ] A compile error => It compiles, but the compiler warns that the Future is unused.

:: text What .await does
`.await` inside another `async fn` means: "poll this Future. If it's `Pending`, I'm `Pending` too — give control back to the runtime".

That makes a chain: the runtime polls the outer Future, which polls the inner one, and so on all the way down. Somewhere at the bottom there's real waiting: a timer, the network, a file.

:: code
```rust
use std::future::Future;
use std::pin::pin;
use std::task::{Context, Poll, Waker};

fn block_on<F: Future>(fut: F) -> F::Output {
    let mut fut = pin!(fut);
    let mut cx = Context::from_waker(Waker::noop());
    loop {
        if let Poll::Ready(v) = fut.as_mut().poll(&mut cx) {
            return v;
        }
    }
}

async fn price() -> u32 { 100 }
async fn tax(p: u32) -> u32 { p / 5 }

async fn total() -> u32 {
    let p = price().await;
    let t = tax(p).await;
    p + t
}

fn main() {
    println!("{}", block_on(total()));
}
```
```out
120
```

:: deep Waker: how not to poll for nothing
Our `block_on` polls the Future in an endless loop. If the Future waits a second for the network, the CPU spins idly.

Real runtimes are smarter. The `Context` holds a **Waker** — an "alarm clock". A Future that returned `Pending` stores it and calls `wake()` when the data arrives. The runtime polls only the Futures that were "woken up".

`Waker::noop()` in our example is an alarm that does nothing. Good enough for a toy runtime: we poll all the time anyway.

And `pin!` is needed because a Future made from an `async fn` may hold references **to itself** (to its own local variables). Such an object must not move in memory after the first `poll`. `Pin` is the promise "I won't move it". More in the `select` lesson.

:: recap
- An `async fn` returns a Future — "the result comes later".
- A Future is lazy: it works only while it's polled (`poll`).
- The runtime does the polling. `.await` passes the polling deeper.

## LESSON a09-2 | tokio and join! | 8
:: goals
- Run an async program on tokio
- Do several waits at once with `join!`

:: text tokio — a real runtime
`tokio` can do everything our toy `block_on` can't: timers, networking, files, many threads. You add it with one line above `main`:

```rust
#[tokio::main]
async fn main() {
    // you can write .await here
}
```
The attribute turns `async fn main` into a normal `main` that starts the runtime.

:: code
```rust
use std::time::Duration;
use tokio::time::sleep;

async fn cook(name: &str, secs: u64) -> String {
    sleep(Duration::from_millis(secs * 100)).await;
    format!("{name} is ready")
}

#[tokio::main]
async fn main() {
    let start = std::time::Instant::now();
    let a = cook("tea", 3).await;
    let b = cook("toast", 2).await;
    println!("{a}, {b}");
    println!("one by one: ~{} ms", start.elapsed().as_millis() / 100 * 100);
}
```
crates: yes
```out
tea is ready, toast is ready
one by one: ~500 ms
```
`.await` one after another — **in turn**: 300 + 200 = 500 ms.

:: text join! — wait for everything at once
`tokio::join!(a, b, c)` runs several Futures **at the same time** and waits until all of them finish. It returns a tuple of results.

> **Analogy:** turning on the kettle and the toaster at the same time, instead of waiting for the kettle before switching on the toaster.

:: code
```rust
use std::time::Duration;
use tokio::time::sleep;

async fn cook(name: &str, secs: u64) -> String {
    sleep(Duration::from_millis(secs * 100)).await;
    format!("{name} is ready")
}

#[tokio::main]
async fn main() {
    let start = std::time::Instant::now();
    let (a, b) = tokio::join!(cook("tea", 3), cook("toast", 2));
    println!("{a}, {b}");
    println!("together: ~{} ms", start.elapsed().as_millis() / 100 * 100);
}
```
crates: yes
```out
tea is ready, toast is ready
together: ~300 ms
```
300 ms, not 500: while we waited for the tea, the toast was toasting too.

:: quiz
Three requests of 1 second each. How long does `join!` take for all three?
[ ] 3 seconds => That's if you `.await` them one by one.
[x] About 1 second => Right. They wait at the same time.
[ ] 0 seconds => You still have to wait.

:: text Important: join! is not threads
`join!` works on **one** thread. Tasks take turns making progress while others wait. So it helps with **waiting** (network, timers), but doesn't speed up heavy computation. For computation — rayon or threads.

:: recap
- `#[tokio::main]` — run an async `main` on tokio.
- `.await` one by one — the times add up.
- `tokio::join!(a, b)` — wait at once; the time is the longest one.

## LESSON a09-3 | spawn and channels | 8
:: goals
- Start independent tasks with `tokio::spawn`
- Pass data between tasks through a channel

:: text spawn — a separate task
`tokio::spawn(future)` hands the Future to the runtime as an **independent task**. It starts working right away, even if you're not waiting for its result yet. It returns a `JoinHandle` — use it to wait for the result.

Similar to `thread::spawn`, but tasks are **lightweight**: you can start thousands of them.

:: code
```rust
use std::time::Duration;
use tokio::time::sleep;

#[tokio::main]
async fn main() {
    let mut handles = Vec::new();
    for id in 1..=3 {
        handles.push(tokio::spawn(async move {
            sleep(Duration::from_millis(30 * (4 - id))).await;
            println!("task {id} finished");
            id * 10
        }));
    }
    let mut sum = 0;
    for h in handles {
        sum += h.await.unwrap();
    }
    println!("sum: {sum}");
}
```
crates: yes
```out
task 3 finished
task 2 finished
task 1 finished
sum: 60
```
The tasks finished in reverse order (the third has the shortest sleep), but we collected the results in order.

:: text Why async move
`tokio::spawn` requires `'static`, just like `thread::spawn`: the task may outlive the function. So you almost always write `async move { ... }` — to take the needed data inside.

:: text Channels between tasks
tokio has its own channels: `tokio::sync::mpsc`. Like with threads, except sending and receiving use `.await`.

```rust
let (tx, mut rx) = tokio::sync::mpsc::channel(16); // 16 is the queue size
tx.send(value).await.unwrap();
while let Some(v) = rx.recv().await { ... }
```
When all senders (`tx`) are dropped, `recv()` returns `None` — the loop ends.

:: code
```rust
use tokio::sync::mpsc;

#[tokio::main]
async fn main() {
    let (tx, mut rx) = mpsc::channel(8);
    for worker in 1..=3 {
        let tx = tx.clone();
        tokio::spawn(async move {
            tx.send(worker * worker).await.unwrap();
        });
    }
    drop(tx); // the main sender is no longer needed

    let mut got = Vec::new();
    while let Some(v) = rx.recv().await {
        got.push(v);
    }
    got.sort();
    println!("{got:?}");
}
```
crates: yes
```out
[1, 4, 9]
```
Without `drop(tx)` the loop would wait forever: as long as any sender is alive, the channel stays open.

:: quiz
Why write `drop(tx)` after the `for` loop with `tx.clone()`?
[x] So the channel closes once the tasks have sent their values, and `recv()` returns `None` => Right.
[ ] To free memory => Not the main point.
[ ] Otherwise the tasks won't start => They will, but the receive loop won't end.

:: recap
- `tokio::spawn(async move { ... })` — an independent lightweight task.
- `handle.await` — wait for its result.
- `mpsc::channel` + `send().await` / `recv().await`. All `tx` dropped → `None`.

## LESSON a09-4 | select! and timeouts | 7
:: goals
- Wait for "whatever happens first" with `select!`
- Put a time limit on waiting with `timeout`

:: text select! — who's first
`tokio::select!` waits on **several** Futures and takes the result of the **first** one to finish. The rest are cancelled.

```rust
tokio::select! {
    v = task_a => println!("A was first: {v}"),
    v = task_b => println!("B was first: {v}"),
}
```
> **Analogy:** waiting for a bus at two stops at once. Whichever bus comes first is the one you take.

:: code
```rust
use std::time::Duration;
use tokio::time::sleep;

async fn server(name: &str, ms: u64) -> String {
    sleep(Duration::from_millis(ms)).await;
    format!("reply from {name}")
}

#[tokio::main]
async fn main() {
    tokio::select! {
        r = server("Europe", 120) => println!("{r}"),
        r = server("Asia", 40) => println!("{r}"),
    }
}
```
crates: yes
```out
reply from Asia
```
We didn't even wait for the slow server: its Future was simply dropped.

:: text timeout — limit the wait
A common `select!` case is "the result, or time's up". There's a ready-made function for it:

```rust
use tokio::time::{timeout, Duration};

match timeout(Duration::from_secs(2), request()).await {
    Ok(reply) => ...,
    Err(_) => println!("too slow"),
}
```

:: code
```rust
use std::time::Duration;
use tokio::time::{sleep, timeout};

async fn slow_answer() -> u32 {
    sleep(Duration::from_millis(500)).await;
    42
}

#[tokio::main]
async fn main() {
    match timeout(Duration::from_millis(100), slow_answer()).await {
        Ok(v) => println!("answer: {v}"),
        Err(_) => println!("time's up"),
    }
    match timeout(Duration::from_millis(900), slow_answer()).await {
        Ok(v) => println!("answer: {v}"),
        Err(_) => println!("time's up"),
    }
}
```
crates: yes
```out
time's up
answer: 42
```

:: quiz
What happens to the other `select!` branches when one finishes?
[ ] They keep working in the background => No, their Futures are dropped.
[x] They are cancelled => Right. That's why cancelling midway must not corrupt data.
[ ] They wait their turn => `select!` takes only one result.

:: deep Cancellation and Pin
In async Rust, cancelling a task = **stop polling it and drop** the Future. Cancellation can happen at any `.await`. So write code that keeps data consistent between two `.await`s. For example, don't hold a "half-written" file while waiting.

About `Pin`: a Future from an `async fn` stores its local variables inside itself. If one variable is a reference to another and the Future is moved in memory, the reference would point to nothing. `Pin<&mut F>` guarantees "I won't move it anymore". `tokio::pin!` or `std::pin::pin!` fix a Future in place when it must be polled several times (for example, in a `select!` inside a loop).

:: recap
- `select!` — the first to finish wins, the rest are cancelled.
- `timeout(duration, future)` → `Ok(result)` or `Err(time's up)`.
- Cancellation can happen at any `.await`.

use std::time::Duration;
use tokio::time::{sleep, timeout};

async fn slow() -> &'static str {
    sleep(Duration::from_millis(300)).await;
    "the real answer"
}

#[tokio::main]
async fn main() {
    let answer = timeout(Duration::from_millis(50), slow()).await.unwrap_or("fallback answer");

```

```
