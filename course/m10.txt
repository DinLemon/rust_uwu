# MODULE m10 | Обработка ошибок | Что делать, когда что-то пошло не так

## LESSON m10-1 | panic! — аварийная остановка | 5
:: goals
- Что такое паника
- Когда паниковать нормально

:: text Два вида проблем
1. **Неисправимые.** Программа в состоянии, где дальше идти нельзя. Например, баг в логике. Тут — **паника**.
2. **Исправимые.** Файла нет, пользователь ввёл буквы вместо числа. Это нормальная жизнь. Тут — `Result`.

:: code
`panic!` останавливает программу с сообщением.
```rust
fn main() {
    println!("Начинаю");
    let level = 0;
    if level == 0 {
        panic!("Уровень не может быть нулём!");
    }
    println!("Сюда не дойдём");
}
```
Программа напечатает «Начинаю» и остановится с сообщением `panicked at ... Уровень не может быть нулём!`.

:: quiz
Пользователь ввёл «abc» вместо возраста. Что лучше сделать?
[ ] `panic!` => Ошибка ввода — обычное дело. Падать из-за неё грубо.
[x] Вернуть ошибку и попросить ввести снова => Верно. Это исправимая ситуация — для неё `Result`.

:: recap
- Паника — аварийная остановка. Для багов и невозможных ситуаций.
- Ожидаемые проблемы обрабатывают через `Result`.

## LESSON m10-2 | Result: успех или ошибка | 7
:: goals
- Как устроен `Result`
- Разбирать его через `match`

:: text Result — посылка с запиской
```rust
enum Result<T, E> {
    Ok(T),  // всё хорошо, внутри результат
    Err(E), // ошибка, внутри описание
}
```
> Посылка. Внутри либо заказанная вещь (`Ok`), либо записка «товар закончился» (`Err`). Похоже на `Option`, только вместо пустоты — объяснение.

:: code
`parse` превращает текст в число и возвращает `Result`:
```rust
fn main() {
    for input in ["42", "сорок два"] {
        match input.parse::<i32>() {
            Ok(n) => println!("Число: {n}"),
            Err(e) => println!("Не число «{input}»: {e}"),
        }
    }
}
```
```out
Число: 42
Не число «сорок два»: invalid digit found in string
```
`::<i32>` говорит `parse`, какое число мы хотим.

:: text Свой Result
Функция сама может вернуть `Result`:

```rust
fn check_age(age: i32) -> Result<i32, String> {
    if age < 0 {
        Err(String::from("Возраст не бывает отрицательным"))
    } else {
        Ok(age)
    }
}
```

:: quiz
Что вернёт `"7".parse::<i32>()`?
[x] `Ok(7)` => Верно. Разбор удался — результат в `Ok`.
[ ] `7` => `parse` всегда заворачивает ответ в `Result`.
[ ] `Some(7)` => `Some` — это `Option`. У `parse` тип `Result`.

:: recap
- `Result<T, E>`: `Ok(значение)` или `Err(ошибка)`.
- Разбирать через `match`, как Option.
- `parse::<i32>()` возвращает `Result`.

## LESSON m10-3 | unwrap, expect и ? | 7
:: goals
- Быстрые способы открыть Result
- Передавать ошибку наверх оператором `?`

:: text unwrap и expect
- `unwrap()` — достать `Ok`, а при `Err` — паника.
- `expect("сообщение")` — то же, но со своим текстом паники. Удобнее искать, где упало.

> Используй их в примерах и там, где ошибка правда невозможна. В настоящей программе — осторожно.

:: text Оператор ? — «если ошибка, отдай её наверх»
Знак `?` после `Result`:
- если `Ok(x)` — даёт `x` и идёт дальше;
- если `Err(e)` — сразу **возвращает** эту ошибку из функции.

```rust
fn sum(a: &str, b: &str) -> Result<i32, std::num::ParseIntError> {
    let x = a.parse::<i32>()?;
    let y = b.parse::<i32>()?;
    Ok(x + y)
}
```
!> `?` работает только в функции, которая сама возвращает `Result` (или `Option`).

:: code
```rust
use std::num::ParseIntError;

fn sum(a: &str, b: &str) -> Result<i32, ParseIntError> {
    let x = a.parse::<i32>()?;
    let y = b.parse::<i32>()?;
    Ok(x + y)
}

fn main() {
    println!("{:?}", sum("2", "3"));
    println!("{:?}", sum("2", "три"));
}
```
```out
Ok(5)
Err(ParseIntError { kind: InvalidDigit })
```

:: quiz
Что делает `?`, если результат — `Err`?
[ ] Паникует => Паникует `unwrap`. А `?` мягче.
[x] Возвращает ошибку из текущей функции => Верно. Пусть разбирается тот, кто вызвал.
[ ] Пропускает строку => Ошибку нельзя просто пропустить: функция заканчивается.

:: task
Допиши функцию с `?`: она разбирает два числа из строк и возвращает их произведение.
```rust
use std::num::ParseIntError;

fn multiply(a: &str, b: &str) -> Result<i32, ParseIntError> {
    // твой код с ?
}

fn main() {
    println!("{:?}", multiply("6", "7"));
    println!("{}", multiply("6", "x").is_err());
}
```
```solution
use std::num::ParseIntError;

fn multiply(a: &str, b: &str) -> Result<i32, ParseIntError> {
    let x: i32 = a.parse()?;
    let y: i32 = b.parse()?;
    Ok(x * y)
}

fn main() {
    println!("{:?}", multiply("6", "7"));
    println!("{}", multiply("6", "x").is_err());
}
```
```expect
Ok(42)
true
```
hint: `let x: i32 = a.parse()?;` — то же для `b`.
hint: В конце верни `Ok(x * y)`.

:: recap
- `unwrap()` / `expect("...")` — достать или запаниковать.
- `?` — достать или вернуть ошибку наверх.
- `?` работает в функциях, которые возвращают `Result`/`Option`.

## LESSON m10-4 | Свои ошибки | 6
:: goals
- Описать возможные ошибки через `enum`
- Вернуть `Result` из `main`

:: text Ошибки как перечисление
Хороший приём: перечислить все ошибки своей функции в `enum`. Тогда вызывающий код точно знает, что может пойти не так.

```rust
#[derive(Debug)]
enum AgeError {
    NotANumber,
    Negative,
    TooOld,
}
```

:: code
```rust
#[derive(Debug)]
enum AgeError {
    NotANumber,
    Negative,
    TooOld,
}

fn parse_age(s: &str) -> Result<u32, AgeError> {
    let n: i64 = s.trim().parse().map_err(|_| AgeError::NotANumber)?;
    if n < 0 {
        return Err(AgeError::Negative);
    }
    if n > 150 {
        return Err(AgeError::TooOld);
    }
    Ok(n as u32)
}

fn main() {
    for s in ["30", "-5", "сто", "200"] {
        println!("{s}: {:?}", parse_age(s));
    }
}
```
```out
30: Ok(30)
-5: Err(Negative)
сто: Err(NotANumber)
200: Err(TooOld)
```
`map_err` превращает одну ошибку в другую — здесь ошибку `parse` в нашу `NotANumber`.

:: text main тоже может вернуть Result
Тогда внутри `main` можно использовать `?`:

```rust
fn main() -> Result<(), String> {
    let n: i32 = "5".parse().map_err(|_| "не число".to_string())?;
    println!("{n}");
    Ok(())
}
```
`()` — «пустое значение»: успех без результата.

:: quiz
Зачем описывать ошибки через `enum`, а не просто текстом?
[x] Вызывающий код может разобрать каждую ошибку через `match` => Верно. А по тексту надёжно разобрать нельзя.
[ ] Так программа работает быстрее => Дело не в скорости, а в понятности и надёжности.
[ ] Компилятор не разрешает текстовые ошибки => Разрешает: `Result<T, String>` вполне законен.

:: recap
- Ошибки удобно описывать своим `enum`.
- `map_err` превращает чужую ошибку в свою.
- `fn main() -> Result<(), E>` разрешает `?` в `main`.
